Field guide

One prompt in. A tested, graded product out.

The harness turns a short product prompt into a working app by separating creation from judgment: one agent plans, one builds, one grades the running app with a skeptical eye. Recurring QA failures feed the anti-slop loop, so each run starts smarter than the last.

The machine

Three agents, one circuit

Every sprint travels the same circuit. The Generator never has final say on its own work: a mechanical gate checks lints and artifacts, then the Evaluator tests the live app and grades it against rubrics. Fail, and the work goes back — up to three rounds per sprint.

The crew

Who does what

Each agent runs in its own isolated context and communicates only through files in docs/ — the Evaluator never sees the Generator's self-justification, only what landed on disk. OpenCode runs all three phases on the model you set via HARNESS_MODEL (default anthropic/claude-sonnet-4-5).

Planner

anthropic/claude-sonnet-4-5

Expands your one-line prompt into a full spec, sprint plan, and status tracker. With no design brief, it defines the visual language in docs/spec.md from your product prompt.

Generator

anthropic/claude-sonnet-4-5

Builds one sprint at a time against a written contract. Every commit must pass the pre-commit hook: sandbox, lints, secret scan.

Evaluator

anthropic/claude-sonnet-4-5

Starts the app and tests every acceptance criterion with Playwright, then grades six weighted criteria. Skeptical by instruction: “it mostly works” is a fail.

Anti-slop

bun gc:weekly

QA failures land in .gc-cache/. Review recurring patterns weekly and promote them into lint rules or guardrails.

Phase 00

Starting a product

This repo is a harness template, not your app. Copy it once per product, run with OpenCode, and keep the first run small enough that you can watch cost and scope.

Copy the template — don’t dogfood it

The generated app lands under app/. Harness infrastructure stays at the repo root. Dogfooding the template pollutes its history — start each product from a sibling copy: 

cp -R tri-agent-harness-opencode ../my-product
cd ../my-product && rm -rf .git && git init
bun install && bun run setup
cp .env.example .env.local

Recurring QA failures feed the anti-slop toolbox (bun gc:weekly) so you can promote patterns into lint rules between runs.

Use OpenCode CLI

The canonical entry point is ./opencode-harness.sh. You need the OpenCode CLI installed and authenticated. Agent definitions live in .opencode/agents/; full personas in agents/.

Scope the prompt — cost is real

A vague “build me a SaaS” prompt routinely plans 8–10 sprints. Each sprint can burn multiple Generator and Evaluator sessions. Cap the blast radius until you trust the plan: 

# one sprint per invocation (re-run to continue)
HARNESS_MAX_SPRINTS_PER_RUN=1 ./opencode-harness.sh "Build a kanban board for film production crews"

# or ask before each sprint (default on a fresh project)
HARNESS_PAUSE=sprint ./opencode-harness.sh "..."

Expect the first-run pause

On a fresh project (no docs/sprint-status.md yet) the harness sets HARNESS_PAUSE=sprint automatically. Watch the plan, then answer a for the rest of the run, or set HARNESS_PAUSE=off / HARNESS_YES=1 for full autonomy.

Override the OpenCode model if needed: HARNESS_MODEL=anthropic/claude-sonnet-4-5.

Optional: steer design before planning

Copy docs/templates/design-brief.md to design/brief.md if you already know the visual direction. With an empty design/, the Planner defines the design language in docs/spec.md from your prompt.

Bringing a full product plan from another chat? That helps — see Planning with another agent for what to keep vs strip before you paste it into the prompt.

Start (or resume) the build

./opencode-harness.sh "Build a kanban app for film production crews"

# optional: allow up to 5 QA rounds per sprint
./opencode-harness.sh "..." 5

State lives in docs/sprint-status.md. Interrupted? Re-run the same command — it resumes from the first sprint not in Pass or Skipped.

When something fails on setup rather than product bugs, jump to Field notes. Autonomy uses --dangerously-skip-permissions — hooks catch bad commits, not bad commands.

Input shape

Planning with another agent

The prompt you pass to ./opencode-harness.sh does not have to be a one-liner. A product plan drafted in another chat or agent usually helps the Planner — richer intent means fewer invented requirements. It does not change the harness architecture: the Planner still writes the canonical docs/spec.md and sprint plan.

In your pre-planEffect
Product goals, users, features, UX flows Helps — better input for the spec
Design direction / brand rules Prefer design/brief.md (authoritative) over burying it in the prompt
Non-negotiable constraints Prefer design/constraints.md, or say explicitly “do not expand beyond this scope”
Stack, file layouts, “implement X with Y” Risk — Planner stays high-level; wrong implementation detail cascades to Generator
Pre-cut sprints Hints only — Planner re-slices into the harness shape (typically 4–8 sprints; Sprint 1 = skeleton)

Practical recipe: keep the other agent’s output as a product brief, strip implementation prescriptions, park visuals in design/brief.md, then run the harness. The Planner may still ambition-expand unless you constrain it — that is intentional, but easy to overshoot on cost. See Starting a product for caps like HARNESS_MAX_SPRINTS_PER_RUN=1.

Phase 01 → 03

Anatomy of a run

A first sprint typically takes 30–90 minutes wall-clock. The Evaluator is the slow part by design — it exercises real user flows in a real browser, not just element presence.

5–15 min

Planning

The Planner writes the spec, sprint plan, and status tracker, and fills AGENTS.md with the design language.

docs/spec.md · docs/sprint-plan.md · docs/sprint-status.md
10–30 min

Build (sprint N)

The Generator writes the sprint contract, implements it, commits through the pre-commit hook, and marks the sprint “Ready for QA”.

docs/sprint-N-contract.md · app/ code
1–5 min

Pre-QA gate

Deterministic checks — lints, required artifacts — before any expensive judgment. A gate failure returns to the Generator and consumes a QA round, same as an Evaluator failure.

docs/mechanical-checks-sprint-N.md
15–45 min

Evaluation pass fail

Playwright testing of every acceptance criterion, six weighted scores with hard thresholds, and a written verdict. Fail sends the work back with an actionable bug list; pass advances to the next sprint.

docs/qa-report-sprint-N.md · sprint status updated
weekly

Anti-slop review

QA failures land in .gc-cache/. Run bun gc:weekly to review recurring patterns and promote them into lint rules or guardrails before the next product run.

On persistent failure the harness halts by default after the max QA rounds so you can review the report. Set HARNESS_ON_MAX_ROUNDS=advance to mark the sprint skipped and press on.

How to run

Autonomous loop

Autonomous — ./opencode-harness.sh

The only supported path. Each phase runs as a separate opencode run invocation, fully hands-off until pass, halt, or a pause you configured (HARNESS_PAUSE=sprint asks before each sprint).

An artifact watchdog stops hung agents once phase outputs land on disk. Optional: HARNESS_OPENCODE_ATTACH to attach to opencode serve.

Product under app/

The Generator scaffolds your application in app/ — not at the repo root. Harness infrastructure stays at the repo root.

From sprint 2 onward, the pre-QA gate requires app/package.json and source under app/. See app/README.md.

Artifacts: how to read a run from disk

Agents hand off through files, never through conversation. That means the whole run is inspectable — and resumable — from these paths.

The return wire

How the harness learns

This OpenCode repo logs QA failures for the anti-slop loop (bun gc:weekly). For the full learning loop, use tri-agent-harness.

Fig. 2 — capture → distill → inject → escalate → graduate

# anti-slop toolbox
bun gc:weekly     # review recurring failures → guardrail proposals

Guardrail proposals are the only human gate: review the draft in docs/proposals/, commit the rule if you agree, and mark the ledger entry graduated. The lesson leaves the prompt; the machine enforces it forever.

When it goes sideways

Field notes: first-run failure modes

The harness now fails fast and loud on all of these — but knowing the symptom saves you a debugging detour. Every one of them is cheap to fix.

SymptomCauseFix
"WARNING: guardrails are OFF" at startup Not a git repository — hooks, secret scan, and lint gate can't install git init && bun install && bun run setup
Preflight: OpenCode CLI missing opencode not on PATH or not authenticated Install the OpenCode CLI; run opencode run once to verify
Gate fails: "No application product found by sprint 2" Generator scaffolded outside app/ Move the product to app/package.json and app/src/ — see app/README.md
QA round 1 fails on setup, not bugs Playwright browsers missing, or the dev-server port is taken npx playwright install; free the port before re-running
Loop stops: "unrecognized status" in a sprint row A hand-edited (or agent-mangled) docs/sprint-status.md status cell Use exactly: Not started, In progress, Ready for QA, Pass, Fail, Skipped
Secret scan feels thin gitleaks not installed — fallback is a 3-pattern regex brew install gitleaks
Run costs more than expected Fully autonomous default after the first run; ambitious plans mean many sprints × QA rounds Scope the prompt; HARNESS_MAX_SPRINTS_PER_RUN=1 or HARNESS_PAUSE=sprint

Two structural facts worth internalizing: the generated app lives under app/ (see Starting a product), and agents run with elevated permissions — the sandbox rules are instructions to the agents, not OS-level enforcement.
